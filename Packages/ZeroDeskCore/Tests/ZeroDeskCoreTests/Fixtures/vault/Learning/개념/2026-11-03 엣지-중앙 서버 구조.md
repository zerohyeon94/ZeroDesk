# 엣지-중앙 서버 구조

> 2026-11-03 · 이번 달 주제: 시스템 전체 한 바퀴 · 예상 20~30분

## 한 문장으로

엣지-중앙 서버 구조는 **바로 판단해야 하는 일은 현장 장비(엣지)가 직접 하고, 여러 장비를 모아 보고·관리·저장하는 일은 중앙 서버가 맡도록 일을 나누는 방식**이다.

- **엣지(edge):** "가장자리"라는 뜻이다. 데이터가 생기는 현장, 즉 카메라·센서 옆에 있는 장비를 말한다.
- **중앙 서버:** 여러 엣지 장비가 연결되는 한 곳의 서버다. 클라우드일 수도 있고 회사 안 서버실일 수도 있다.

위키백과는 엣지 컴퓨팅을 "계산과 데이터 저장을 데이터가 생기는 곳 가까이로 가져오는 분산 컴퓨팅 방식"이라고 정의한다. 목적은 두 가지다. **응답을 빠르게(지연 시간 줄이기)**, **네트워크로 보내는 양을 줄이기(대역폭 아끼기)**.

## 비유

**지점과 본사**로 생각해 보자.

- 지점(엣지)에는 직원이 있어서 손님이 오면 그 자리에서 바로 응대한다. 본사에 전화해서 "이 손님 받아도 되나요?"라고 묻지 않는다.
- 지점은 하루 일을 **요약해서** 본사(중앙 서버)에 보고한다. 손님 한 명 한 명의 대화를 다 녹음해서 보내지 않는다.
- 본사는 모든 지점의 보고를 모아 비교하고, 새 업무 지침을 만들어 지점에 내려보낸다.
- 본사와 전화가 끊겨도 지점은 문을 닫지 않는다. 보고서를 쌓아 두었다가 연결되면 보낸다.

**비유가 틀리는 지점:** 지점 직원은 스스로 판단하는 사람이지만, 엣지 장비는 **본사가 내려보낸 프로그램과 설정대로만** 움직인다. 또 지점은 보고서를 몇 주씩 쌓아 둘 수 있지만, 엣지 장비는 디스크 크기와 보관 기간 설정 때문에 **오래 끊기면 쌓아 둔 데이터를 잃을 수 있다**(아래 "어디서 깨지나").

## 흐름

### 1) 장비 안에는 누가 사는가

이 노트에서는 엣지 장비 안의 프로그램을 두 종류로 나눈다.

- **AI 엔진:** 카메라 영상이나 센서 값을 받아 학습된 모델로 판단(추론)하는 프로그램. **추론(inference)** 은 이미 학습된 모델에 새 입력을 넣어 결과를 얻는 일이다.
- **에이전트(agent):** 장비 안에 상주하면서 중앙 서버와 연락하는 관리 프로그램. 중앙이 내려보낸 설정·프로그램을 받아 설치하고, 장비 상태를 중앙에 보고하고, 결과를 중앙으로 전달한다.

실제로는 "에이전트"라는 단어의 뜻이 제품마다 조금씩 다르다. 예를 들어 Azure IoT Edge는 장비 안의 역할을 **EdgeAgent**(배포 상태를 중앙에 보고하는 관리자)와 **IoT Edge hub**(메시지를 저장하고 전달하는 우체국)로 나눈다. 이 노트는 둘을 합쳐 "에이전트"라고 부른다.

### 2) 정상일 때의 흐름

```text
 [카메라·센서]
      │  원본 데이터 (영상, 측정값) — 양이 많다
      ▼
 ┌──────────── 엣지 장비 ─────────────┐
 │  AI 엔진: 그 자리에서 추론          │
 │     │  결과만 (예: "사람 감지 1건") │ ← 양이 적다
 │     ▼                               │
 │  에이전트: 결과·상태를 묶어서 전송   │
 │     ▲                               │
 └─────┼───────────────────────────────┘
       │  ↑ 결과·상태 보고      ↓ 설정·새 모델·새 프로그램
       ▼
 ┌──────────── 중앙 서버 ─────────────┐
 │  여러 장비의 결과를 모아 저장        │
 │  장비 목록·상태 관리                 │
 │  새 버전 배포                        │
 └─────┬───────────────────────────────┘
       ▼
 [웹 화면] 사람이 결과를 보고 설정을 바꾼다
```

핵심은 **원본은 엣지에 머물고, 결과만 위로 올라간다**는 점이다. 위키백과의 예시가 이것을 잘 보여 준다. 음성 인식을 장비에서 하면 녹음 파일 대신 **인식된 글자만** 클라우드로 보내므로 대역폭이 크게 줄어든다.

### 3) 역할 나누기

- **영상·센서 추론 → 엣지.** 바로 반응해야 하고, 원본이 너무 크다.
- **원본 데이터 보관 → 주로 엣지.** 보내는 양을 줄이고, 민감한 데이터가 밖으로 덜 나간다.
- **여러 장비 결과 모으기·검색 → 중앙.** 한 곳에 모여야 비교·통계가 된다.
- **장비 상태 보기 → 중앙 (웹).** 사람이 한 화면에서 전체를 본다.
- **새 모델·프로그램 배포 → 중앙에서 엣지로.** 지침은 본사가 만든다.

AWS IoT Greengrass 공식 문서도 같은 나눔을 설명한다. 장비가 **자기가 만든 데이터에 대해 현장에서 동작하고**, **머신러닝 모델로 예측을 실행하고**, **데이터를 걸러내고 모으고(filter and aggregate)**, 그다음 클라우드로 내보낸다. 소프트웨어는 **컴포넌트(component)** 라는 단위로 묶어 클라우드에서 장비로 배포한다.

### 4) 네트워크가 끊겼다가 돌아올 때

Azure IoT Edge 공식 문서가 설명하는 오프라인 흐름을 일반화하면 이렇다.

```text
 ① 처음 한 번은 반드시 중앙과 연결해 동기화한다
     (설정, 메시지 보관 규칙 등을 받아 둔다)
 ② 연결이 끊긴다
     - 장비와 그 안의 프로그램은 계속 돈다
     - 위로 보낼 메시지는 장비 디스크에 쌓아 둔다 (저장 후 전달)
 ③ 연결이 돌아온다
     - 쌓아 둔 메시지를 바로 보내기 시작한다 (쌓인 순서대로)
     - "중앙이 원하는 설정"과 "장비가 보고한 설정"의 차이를 맞춘다
```

- **저장 후 전달(store and forward):** 보낼 수 없을 때 일단 저장했다가, 보낼 수 있게 되면 전달하는 방식.
- 다시 연결된 뒤 전달 속도는 연결 속도와 중앙 쪽 지연에 달려 있어서, 쌓인 양이 많으면 다 올라가는 데 시간이 걸린다.

이 흐름을 코드로 아주 단순하게 그리면 다음과 같다. 실제 제품 코드가 아니라 역할을 보여 주는 의사 코드다.

```python
# 에이전트의 한 바퀴를 단순화한 의사 코드 (읽기만 하면 된다)

def agent_loop(engine, outbox, server):
    frame = camera.read()            # 현장 원본 데이터: 엣지 밖으로 나가지 않는다
    result = engine.infer(frame)     # AI 엔진이 장비 안에서 추론한다
    outbox.append(result)            # 보낼 결과를 먼저 장비 디스크의 보관함에 넣는다

    if server.is_connected():
        # 보관함에 쌓인 것을 들어온 순서대로 꺼내 중앙으로 보낸다
        while outbox:
            server.send(outbox.pop_oldest())
        # 중앙이 원하는 설정·버전과 지금 장비 상태를 비교해 맞춘다
        apply(server.desired_config())
        server.report(device_status())
    # 연결이 없으면 아무것도 보내지 않고 다음 바퀴로 넘어간다
```

## 어디서 깨지나

**1. 오래 끊기면 쌓아 둔 메시지가 사라진다**
저장 후 전달에는 한계가 두 가지 있다. **보관 기간(TTL)** 과 **디스크 크기**다.
- **TTL(time to live):** 메시지가 전달되기를 기다릴 수 있는 최대 시간. 이 시간이 지나면 메시지는 만료된다.
- Azure IoT Edge의 기본 TTL은 **7,200초(2시간)** 다. 그러니 기본 설정 그대로 3시간 끊기면, 끊긴 직후 쌓인 메시지는 다시 연결되기 전에 만료될 수 있다. 오래 끊길 수 있는 현장이라면 TTL을 늘리고 저장 공간을 더 주라고 문서가 권한다.

**2. 중앙 화면이 "정상"이라고 거짓말할 수 있다**
상태 보고도 네트워크를 타고 올라간다. 장비가 끊기면 새 상태를 보고하지 못하므로, 중앙 화면에는 **마지막으로 받은 상태가 그대로 남는다.** Azure 문서는 장비가 인터넷에 연결되어 있지 않아도 포털의 장비 상태가 **200 OK**로 남아 있을 수 있다고 적고 있다. 그래서 "마지막 보고 시각"을 함께 봐야 한다.

**3. 처음 한 번도 연결하지 못한 장비는 오프라인으로 일할 준비가 안 되어 있다**
Azure 문서 기준으로 오프라인 동작은 **최소 한 번 중앙과 동기화한 뒤**에 가능하다. 설치만 하고 연결을 못 한 장비는 받아 둔 설정이 없다.

**4. 장비가 많아질수록 관리가 어려워진다**
위키백과는 엣지 구조의 어려움으로 여러 곳에 흩어진 장비의 장애 대응, 성능이 서로 다른 장비들, 개별 장비 고장, 그리고 자원이 부족한 장비라서 보안 방법을 고르는 데 제약이 있다는 점을 꼽는다. 중앙 한 대를 지키던 문제가 **현장마다 한 대씩 지켜야 하는 문제**로 바뀐다.

**5. 역할을 잘못 나누면 장점이 사라진다**
원본 영상을 전부 중앙으로 올려서 추론하면 대역폭과 지연이 다시 커진다. 반대로 결과 비교·검색까지 장비마다 따로 하면 전체 그림을 볼 곳이 없어진다.

## 이런 시스템에서는

엣지 장비·중앙 서버·웹이 있는 시스템을 위에서 아래로 보면 대개 이렇게 나뉜다.

- **엣지 장비:** 카메라·센서 옆에서 AI 엔진이 추론한다. 에이전트는 결과를 보관함에 쌓아 중앙으로 보내고, 중앙에서 온 설정·모델을 적용하고, 장비 상태를 보고한다. 네트워크가 끊겨도 추론과 저장은 계속한다.
- **중앙 서버:** 장비 목록과 각 장비의 "원하는 설정"을 가지고 있다. 여러 장비가 보낸 결과를 받아 데이터베이스에 저장하고, 새 버전을 장비들에 배포한다.
- **웹:** 사람이 중앙 서버를 통해 결과를 보고, 장비 상태를 확인하고, 설정을 바꾼다. 웹은 장비와 직접 이야기하지 않고 **중앙을 거친다**는 점이 보통의 모양이다.

이 구조를 볼 때 던질 질문 세 가지:
1. 이 일은 **바로 반응**해야 하나? → 그렇다면 엣지.
2. 이 데이터는 **크거나 민감**한가? → 그렇다면 원본은 엣지에 두고 결과만 올린다.
3. 이 일은 **여러 장비를 함께 봐야** 하나? → 그렇다면 중앙.

이번 달은 "시스템 전체 한 바퀴"를 도는 달이다. 오늘은 큰 지도만 그렸고, 장비와 중앙이 실제로 어떤 방식으로 메시지를 주고받는지(통신 방식, 연결 유지와 재연결)는 다음 개념들에서 하나씩 깊게 본다.

## 단어 정리

- **엣지(edge):** 데이터가 생기는 현장 가까이에 있는 장비. 카메라·센서 옆의 작은 컴퓨터.
- **엣지 컴퓨팅:** 계산과 저장을 데이터가 생기는 곳 가까이로 가져오는 분산 컴퓨팅 방식. 지연과 대역폭을 줄인다.
- **중앙 서버:** 여러 엣지 장비가 연결되어 결과를 모으고 장비를 관리하는 서버.
- **지연 시간(latency):** 요청하고 응답을 받기까지 걸리는 시간.
- **대역폭(bandwidth):** 네트워크로 한 번에 보낼 수 있는 데이터 양. 많이 보낼수록 빨리 찬다.
- **추론(inference):** 학습된 모델에 새 입력을 넣어 결과를 얻는 일.
- **AI 엔진:** 이 노트에서 장비 안에서 추론을 맡는 프로그램을 부르는 말.
- **에이전트(agent):** 이 노트에서 장비 안에 상주하며 중앙과 연락하고, 설정·프로그램을 적용하고, 상태와 결과를 보고하는 관리 프로그램을 부르는 말. 제품마다 뜻이 조금 다르다.
- **컴포넌트(component):** AWS IoT Greengrass에서 장비에 배포하는 소프트웨어 묶음의 단위.
- **저장 후 전달(store and forward):** 보낼 수 없을 때 저장했다가 연결되면 전달하는 방식.
- **TTL(time to live):** 메시지가 전달을 기다릴 수 있는 최대 시간. 지나면 만료된다. Azure IoT Edge 기본값은 7,200초(2시간).
- **원하는 설정 / 보고된 설정:** 중앙이 "이렇게 되어 있어야 한다"고 정한 값과, 장비가 "지금 이렇다"고 알린 값. 다시 연결되면 둘의 차이를 맞춘다.
